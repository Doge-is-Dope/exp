# exp workspace

- Create projects as `YYYY-MM-DD-name/` under this root, using the user's local date and copying `scaffold/`. If the destination exists, ask whether to use it or choose another name before proceeding. Keep each project's code, dependencies, local data, and requirements inside it.
- `scaffold/` is a technology-neutral template; `.practice-backups/` holds archived projects. Neither is an active app. Reset only user-selected projects and preserve the toolkit.
- Use the user's goals and acceptance criteria as scope. Keep requirements and important decisions in one existing specification or `SPEC.md`; label unconfirmed assumptions. Explicit user instructions take precedence over skill guidelines; skills do not add product requirements or authorization.
- When resuming a project, read its existing specification, relevant implementation, and verification entrypoints; reconcile recorded status with current files and evidence before choosing the next action. Historical success is not current acceptance. Preserve confirmed decisions; unanswered questions remain unconfirmed, while independent authorized work can continue.
- During implementation, keep a concise current-state summary in the existing specification at meaningful progress, decision, blocker, or delivery boundaries. Record the update time, completed scope, remaining work, unresolved questions, and the next action with its completion condition. Replace obsolete status rather than accumulating a conversation log; link verification evidence from the existing acceptance section. Adapt existing document structure without requiring migration. For read-only requests, questions, or work prohibiting file changes, provide any needed handoff in the response instead.
- Choose technology for the task, existing environment, and user preferences. Make routine reversible decisions independently. Ask only when missing information materially changes the outcome; inspect existing decisions first and continue unaffected work while waiting. Waiting is not confirmation.
- Prioritize readability and ease of extension. Follow the chosen stack's conventional names, formatting, and indentation, including markup and styles; do not compress source to reduce line count. Use templates or components for substantial markup, with data preparation separate from presentation. Organize files by responsibility, keep dependency directions clear, and add abstractions and layers only for demonstrated needs.
- Use established external libraries when they meaningfully simplify implementation or improve maintainability; minimizing dependency count is not a goal by itself. Before introducing a new library, tell the user which library, why it is needed, and any material setup or maintenance impact. This is a notification, not an additional approval gate; honor existing user constraints and required permissions.
- Use subagents when independent work can save time or improve quality; handle simple tasks directly. Give each worker clear scope, ownership, and a checkable deliverable; the main agent owns integration. Isolate overlapping writes.
- Complete authorized implementation through running the application, verifying the requested behavior, and repairing issues caused by the change. Honor planning-only requests. If a deadline is at risk, explain the remaining gap and proposed tradeoff without silently lowering acceptance.
- Before final verification, inspect the final changed and affected source for unclear naming or responsibilities, unnecessary coupling, complex branches, duplicate logic, redundant wording, dead code, and inappropriate hardcoding. Check callers and entrypoints before removing code; retain meaningful constants, protocol names, and defaults. Fix issues introduced by the work before claiming completion; passing tests alone do not establish code quality. Report unrelated existing issues without expanding the refactor.
- Use appropriate native tests, existing static checks, and actual operation. Keep checks proportionate and meaningful; avoid tests that merely restate the implementation. Complete required gates, then broaden or repeat checks only for new edits, failures, or unresolved concerns.
- Local verification using isolated disposable data is part of authorized implementation: run it, repair failures caused by the change, and rerun affected checks without another confirmation. Preserve external-service and user-data boundaries.
- Tests must prepare and clean up their own runtime directories, fixtures, and subprocesses, including on failure. For new projects or changes to setup, verify the documented setup and test commands from a fresh source copy after installing declared dependencies, without pre-existing application data or generated output. Preserve the user's working data when doing this check.
- Default new projects to the chosen stack's native tests and actual operation. Preserve existing project tests, CI, and acceptance gates. Adopt the harness when explicitly requested or already established; a broken harness contract must be repaired, not bypassed. Read `harness/README.md` only for harness work. For harness application delivery, finish source and documentation updates before the final `verify`, then report its evidence without editing fingerprinted files. Later edits require re-verification to claim current acceptance. Documentation-only changes may use focused checks but must not claim an old report is current.
- Report what actually ran, important limitations, and how to start the result. Link the existing specification and evidence rather than repeating them in full. For harness delivery, leave the final result in its report and response after verification; do not update the specification again merely to register that result. Keep communication concise and use the user's preferred language.
